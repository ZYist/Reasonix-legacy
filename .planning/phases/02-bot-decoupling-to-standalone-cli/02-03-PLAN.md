<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| inbound Telegram/Weixin message → host.runTurn | Unauthenticated chat-network text enters the agent loop; boundary enforced by channel allowlist (tg/weixin parallels to qq decideQQAccess). The host defers identity to the channel (same as 02-02 T-02-05). |
| gate-reply text → pauseGate.resolve | Channel reply parsed by consumeReply; spoof defense reuses 02-01 T-02-02 mitigation (default-else = deny/cancel). |
| Weixin QR scan login | First-time login requires the user to scan a QR with their WeChat app — the QR text is generated by runWeixinQrLogin (bot.ts:130) and printed to the terminal; an attacker shoulder-surfing could hijack the session. |
| Telegram bot token | The TELEGRAM_BOT_TOKEN (or equivalent env/config) is loaded into the channel; leakage into logs is an Information Disclosure vector. |
| PID lock (Weixin LOCK if any) | If Weixin has its own lock file analogous to QQ_LOCK_FILE, multiple-instances must not race. Read src/weixin/channel.ts to confirm presence/absence. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-10 | Spoofing | inbound Telegram/Weixin identity | high | accept | Access control stays in-channel (tg/weixin allowlist). weixinCommand/telegramCommand trust channel-vetted text. Reuse D-07 rationale — do not reimplement auth at the command layer. |
| T-02-11 | Tampering | gate consumeReply → pauseGate.resolve (Telegram/Weixin) | high | mitigate | Same mitigation as 02-01 T-02-02 + 02-02 T-02-06: consumePauseReply default-else branches route unknown text to deny/cancel — assert in weixin/telegram adapter unit tests (a separate gate-callbacks test per channel, or factor one test parameterized over channel) that unknown text -> deny. |
| T-02-12 | Spoofing | Weixin QR scan hijack (shoulder-surfing) | medium | accept | The QR is printed to the terminal where the operator runs `reasonix weixin`. Physical-screen shoulder-surfing is out of scope for a CLI tool — accept with rationale: the threat model assumes the operator controls their terminal; we do not gate the QR behind an interactive prompt. If the user wants obscurity, they can pipe stdout through `less` or use SSH. |
| T-02-13 | Information Disclosure | Telegram bot token / Weixin session in logs | medium | mitigate | All weixin.ts/telegram.ts process.stderr.write calls use `t("commands.*", {msg})` interpolated with sanitized Error.message; the channel modules (src/telegram/bot.ts, src/weixin/bot.ts) already load the token from env/config and never print it on the onInfo path. Audit (grep the two new command files): no literal `token`/`apiKey`/`secret` symbol is interpolated into a user-visible string. Verify in the unit tests by simulating an error and asserting the logged string does not contain a token-shaped substring. |
| T-02-14 | Denial of Service | missing SIGINT handler (Telegram/Weixin) | low | mitigate | Same as 02-02 T-02-09 — install SIGINT/SIGTERM cleanup BEFORE channel.start() in both telegram.ts and weixin.ts; assert `grep -n 'SIGINT' src/cli/commands/telegram.ts` line < `grep -n 'channel.start'` line, same for weixin. |
| T-02-15 | Tampering | channel-protocol defect during Weixin QR state machine | low | accept | runWeixinQrLogin is an existing in-channel helper (bot.ts:130) weixin.ts reuses without modification (BOT-02: "迁移现有接入,不重写协议"). Defect risk in the QR state machine is owned by the channel module; weixin.ts only invokes it. Accept: migrating the channel does not introduce new QR-state-machine attack surface. |
| T-02-SC | Tampering | npm installs | high | mitigate | No new npm install this plan — pure TS additions + adapter edits. slopcheck gate not triggered. |
